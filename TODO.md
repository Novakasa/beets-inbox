## Bugs

### ~~Files dropped by ytdl-sub get stuck in "Cataloging…" forever~~ FIXED

Fixed 2026-08-28 by replacing the event-based watcher with a reconciling
`Cataloger` (`services/cataloger.py`): an idempotent `sync()` sweep at
startup + every 30s diffs the inbox directory against the inbox beets DB
in both directions. Missed arrivals (the `.part`-rename case), catalog
failures, and orphan DB rows all self-heal; failures surface as
`catalog_error` in the API/UI. The stuck production items catalog
themselves on the next deploy/restart. watchdog dependency removed.
Decision record: docs/architecture-review-2026-08-28.md, candidate 1.

### Sidecar lookup never finds yt-dlp info.json files

All items in the production inbox have `source_url: null`. The backend
looks for sidecars by *appending* to the audio filename
(`_parse_sidecar`: `track.m4a` → `track.m4a.info.json`), but yt-dlp's
`--write-info-json` *replaces* the extension (`track.m4a` →
`track.info.json`), so if ytdl-sub writes sidecars at all, beets-inbox
never finds them. Fix: try both naming conventions (and confirm the
ytdl-sub preset actually writes info.json — if it doesn't, enable it).

Without sidecars the UI loses source URL / video ID / uploader — exactly
the metadata needed to tell near-duplicate downloads apart (see the two
`nΦra @ Bucht der Träumer:innnen` entries in production, likely the same
video re-downloaded after a YouTube title edit, or two distinct uploads —
undecidable from the API precisely because source_url is missing).

## Design: multiple target libraries, drop categories

Direction (2026-08-28, not yet designed in detail): replace categories
with **one inbox per target beets library**, and support multiple target
libraries in one server instance (concrete driver: split live sets out of
the main collection into their own beets library).

Why: a category today is just a subdirectory of the single inbox with no
downstream meaning — every import lands in the same main library and the
category is forgotten. The distinction that matters (live sets vs. album
collection) is a different *target library*, with different import
behavior (autotag off, different path format, different dedup semantics).

What this simplifies:
- Inbox goes flat: top-level file = single, top-level dir = album group.
  Kills the category nesting layer and the watcher's `rel.parts > 2` rule.
- ytdl-sub subscriptions write directly into the inbox of the library
  their content belongs in.
- Per-library settings (autotag default, beets path format) get a natural
  home; each library gets its own generated beets config pair.

What it costs:
- Config outgrows single-valued env vars → structured config file
  (generated by the nix module); env-var form could remain as a
  single-library shorthand.
- API grows a library dimension (`/api/libraries/{name}/inbox/...`);
  Elm category filter becomes a library switcher.
- Migration of the deployed `inbox/live-sets/` into the new layout.

Open questions to settle at design time:
- Cross-library "everything pending" view, or one library at a time?
- Re-routing an item to a different library from the UI (pre-import move
  between inboxes)?
- Scratchpad DB per library (leaning yes — cheap, full isolation)?
- Is any lightweight labeling *within* an inbox still wanted once
  categories stop doing routing duty?
